# Changelog

Status as of 0.1.0-test.6 (2026-11-09): Skipper is in active development and not released. The current version is 0.1.0-test.6; the README holds the one full status banner. Test builds are for the project's own testing and are not published. Every entry below describes the code of the project, which is added to this repository step by step (documents first). "In code" means that the code and its automated tests exist. It does not mean proven: no probe counts yet, because the stage 1 checker (`cargo xtask stage1-check`, which runs once the code and the probe sheets are published) keeps every item open.

The other pages: [README](../README.md), [user guide](user-guide.md), [install guide](install.md), [tested Claude Code versions](tested-versions.md).

## Unreleased

Not in any build yet: the next test build holds it, and the section of that build takes this entry over.

- **A project that you made before the code folder was made for you gets its code folder when you start work.** Before, such a project (it has its roles, and its `workspace.toml` names no code folder) still refused to start the Lead with "The project's code folder is missing. Enter it under Settings › General.", because Skipper made the code folder only for a new project and at the end of the first start. Now your own Start (Start the Lead, Start the team, Start the whole team, the Start of one role, a fresh Start after its question, "Continue as yesterday"), when the project has no code folder, first makes a folder named `code` inside the project's folder with a new Git repository on the branch `main` and one empty first commit, writes it into the project's settings as the code folder, and then goes on with the start. The Start button at the top and the Start button of a role's page are no longer locked by that message while Git is installed and the project's own folder is not a Git repository itself, because your own Start makes the folder. A repository that is in that `code` folder already is used as it is. A code folder that the project has, whether you typed it or it is not on this PC, is not changed. If Git is not installed, or the project's own folder is a Git repository itself (Skipper makes no repository inside a repository), nothing can be made: the Start buttons stay locked with the old message, which stays the way out, so no click is offered that cannot work; you enter the code folder under Settings › General. If a step does not work although Git is installed and the project's own folder is no repository (Git does not start, the project's settings cannot be saved), nothing is made, the Log page has the row "The code folder of a new project was not made" that names the step, the start goes on all the same and then stops with the old message, which stays the way out. The start of the hidden driver is no person's and makes nothing. The new tests of this entry ran green on a real PC on 2026-11-09: `cf_2_existing_project` (12 tests), the library tests of `skipper-app` (513) and `cf_1_code_folder` of `skipper-core` (10). The Start of a project that was made before the code folder was made for you has not been tried by hand yet.

## 0.1.0-test.6 (2026-11-09)

Not published. A test build, for the project's own testing. It holds everything that the fifth test build holds, and the changes below. Each entry says what you notice first. All of them describe the code and its automated tests as they were written. Nothing here has been seen in the running program on a real PC yet, and an entry that rests on a reading of the code of the window library says so.

- **"Search" and the drawer of a narrow window stay bright and usable after a click elsewhere has closed them.** Before, "Search" (the command palette, opened from the search row at the top left) could come up dimmed and dead: in the fifth test build it was bright the first and the second time and dimmed from the third time on, nothing in it could be clicked, and only Esc closed it. The drawer that holds the sidebar in a narrow window (opened by the Team button) had the same fault. Cause, as read in the code of the window library (egui): each of them is made of two layers of one order, a layer that dims the window and the panel on top of it. A click on the dimming layer, which is the click that closes the panel, lifts the dimming layer above the panel, and the library keeps that order when both layers become visible again in the same frame. At the next opening the dimming layer therefore lay over the panel, painted over it and took every click that was meant for it. A click inside the panel then counted as a click that is not outside it, so it neither closed the panel nor chose an entry. Now the panel is declared a sublayer of the dimming layer in every frame in which it is drawn, and the library puts a sublayer directly above its parent at the end of each pass, whichever of the two was lifted. The other places of the window were looked at: no other pair of a dimming layer and a panel exists, and the dialogs of the window library draw their dimming and their content in one layer, so they cannot have the fault. Limits: this entry rests on a reading of the code of the window library. The four new tests of `skipper-app` (real pointer clicks in the real window, five openings in a row, and an entry that is chosen by a click after the panel was closed three times by a click elsewhere) have not been compiled or run, so that they fail without the change is derived from that code and was not seen. Two dialogs on top of each other (a notice over the Settings window) were not looked at.
- **The Claude sign-in runs without the box, as in a normal terminal.** Before, "Sign in" ran Claude Code's own sign-in inside the protective box, like a role. Inside the box the answer of the browser could not reach the small listener that Claude Code opens on this PC for it (the box closes this PC's own network address to its program), so Claude Code fell back to a page with a code that you had to copy into the panel. Now the sign-in program itself, and only it, starts as it would in a terminal of your own: no protective box, no restricted token and no folder grants. It runs in the same panel and with the same environment as before (the account's folder as Claude Code's configuration folder, the terminal variables and the filtered variables of Windows). It still runs in a job of its own with the limits of a role of that account, so it ends when you cancel or close the panel and when Skipper ends, and it ends by itself after at most ten minutes, which counts as a cancel. The risk that the project accepted with this: a Claude Code that had been tampered with could read your files during those minutes, the vault files and the folders of your other accounts included. The sign-out and the check that asks Claude Code after the sign-in whether the account is signed in stay in the box, and the card still says "Signed in" only on a yes of that check, never without proof. A sign-in is now refused while a role of the account runs ("A role of this account runs. Skipper signs in only while no role of the account runs." and "Stop the roles of the account, then click “Sign in” again."), as the sign-out already was, because a program without a box must not run next to a running session of the account. Since the sign-in program has no box, a protection tier that does not work no longer stops "Sign in"; the check after it makes its box when it runs, and where no box can be made the sign-in goes through and the card says "Sign-in not confirmed", and "Check again" says why. The window's English and German texts have three new lines for the refusal. Limits: this entry and the next one belong together, because without the hand-off of the next entry the page that Claude Code opens by itself may still not reach your browser from inside the sign-in's job. The new tests of this entry, `si_3a_unboxed_sign_in` of `skipper-app` (6 tests), ran green on a real PC on 2026-11-09, together with the library tests of `skipper-app` (513). A real sign-in with this change has not been tried by hand yet.
- **Claude Code hands its sign-in page to Skipper, which opens it, so you only click "Authorize" and copy no code.** Before, the sign-in could end in a page with a code that you copied into the panel (the page of the fifth test build), or in a tab that opened late or not at all. Now Skipper names its own small opener program to Claude Code for this one sign-in, through the variable `BROWSER` that Claude Code reads: a copy of Skipper's hook program, `skipper-open-url.exe`, which Skipper puts into the sign-in's own temporary folder and checks by its hash. Claude Code starts that opener with the address of its page that returns to Claude Code on this PC. The opener passes the address through a pipe that exists for this sign-in only, with a key made for this run, to Skipper. Skipper accepts it only when the key is right, the opener runs inside the sign-in's job, and the address is a whole `https` address on claude.ai, claude.com, platform.claude.com or console.anthropic.com whose path ends in `/oauth/authorize`. Skipper then opens it once in your default browser (the Log page marks that opening as "Automatic"). You click "Authorize" on Anthropic's own page, which Skipper never does for you, and Claude Code in the panel finishes by itself: you paste nothing. If the copy or the pipe cannot be made, or Claude Code does not call the opener, the sign-in still starts and the way of before works: the panel opens the printed address after a wait of four seconds, and a code can be pasted. The name `BROWSER` and the pipe's names reach the sign-in program only: never a sign-out, a status check or a role, and every other caller that names `BROWSER` is refused. The address and the key are never written to the Log, and a refused hand-off leaves no row there yet. Limits: what has not been seen is that the installed Claude Code calls the opener with the address of its returning page and counts its exit as "opened", that its opener process runs inside the sign-in's job, and that the opener opens no console window for a moment. The tests `si_3b_hand_off` of `skipper-app` (12 tests) ran green on a real PC on 2026-11-09. The new tests of `skipper-core` for this entry have not been recorded as run. A real sign-in with the opener has not been tried by hand yet.
- **The working agreement for people and AI tools is in the repository: small pull requests only.** Before, the rules for work on GitHub were spread over several pages, and nothing told an AI tool how to work in the repository. Now `docs/github-workflow.md` is one page of thirteen numbered rules, each marked MUST or SHOULD: the issue first, branch names, commits with the sign-off and no other trailer, one topic per pull request, checks that are green and never weakened, review, squash merge only, labels, versions and tags only by the maintainer, security, dependencies, documentation in the same pull request, and work with AI tools. It points to the numbered rules of the contributing page and repeats none of them in a weaker form. The page says that large pull requests are not allowed: one topic in each pull request, so that it can be accepted or rejected on its own; at most 400 changed lines (added plus removed, tests included), not counting generated files such as `Cargo.lock`, with a written exception only from the maintainer, and with the number set by the workflow page, which other texts repeat; a larger change is split into several pull requests that each pass every check on their own; refactors, renames, formatting and behaviour changes go in separate pull requests; and a pull request that is too big or mixes topics is not reviewed but returned with the request to split it. An AI tool is bound by the same limits and plans the split first. `AGENTS.md` at the top of the repository is the short instruction file that AI tools read (what Skipper is, how to build and test, 19 rules, a map of the crates), `.github/copilot-instructions.md` points to it and to the page, and the README, the contributing page and the pull request template link the page. The template has a new section "AI assistance" and a box that points to the size limit. Nothing in the program changes with this entry, and contributions are still not open: the page says so in its status line. Limits: nothing counts the lines yet, so the maintainer counts them by hand (`git diff --stat`). The new tests of `skipper-core` that pin the page, `AGENTS.md` and the links are part of the document tests `public_docs` (59 tests), which ran green on a real PC on 2026-11-09.
- **The push check can make the first upload onto an empty public repository.** Nothing in the program changes with this entry; it concerns the tool that the project uses to upload its source. Before, the check that every upload passes on the project's build machine refused the first upload into a fresh repository. It takes the scan rules and the scanner from the last reviewed commit of the remote's `main`, and a fresh repository holds only a placeholder with a README and a licence, so no first upload could pass. Now there is one explicit mode for exactly that first upload, started with `--seed` and the placeholder's commit. Everything is checked before anything is sent: the placeholder is the tip of the remote's `main` and `main` is the only branch there; the placeholder holds no scan rules of its own; the pushed history is exactly the placeholder and one commit on top of it, with no merge; the person who starts it names that commit as accepted, because the push brings the files that decide what the scan lets through (the scan rules, the scanner and the push tool itself); the scanner is the one that the build machine made from the pushed commit, with its receipt and its hash; and the scan reads every file of the whole history, with the rules of the pushed commit. The push has one refspec, no force and no tags, and every step prints a line to the log. After this one upload the mode cannot be used again: it is refused against a remote whose `main` holds scan rules, so against every repository that has had its first upload. Without `--seed` every upload is checked exactly as before. Limits: in this one upload the scan rules and the scanner come from the commit that is pushed, so a commit that carried loosened rules and a weakened scanner would pass its own scan. That gap cannot be closed from inside the check. It is covered by the receipt of the build machine, by a second reader of those files, and by a second run, by hand, of the already trusted scanner with the old rules. The 20 new tests of the push tool ran green on a real PC on 2026-11-09 (the launcher tests, under the project's build cap), but no test drives a whole push (job, box and hook) from end to end. The first upload of this repository went through this mode.

The changes above add nothing to "Not built yet" and take nothing from it, and the limits that they leave are named in their own entries.

Cause, as read in the code: Skipper started the Windows program that opens an address inside a short-lived helper job and ended that job as soon as the program returned, which it does at once after it has handed the address to the browser, so the browser that had just been started was ended with it. Now Skipper starts that program (and Explorer, for the button that shows a project's definitions folder) with no helper job of its own, never ends it, and starts it so that it leaves Skipper's own job: the browser is then not capped by Skipper's limits and stays open when Skipper closes. Only Skipper's own main job allows this. The jobs of the roles, of the sign-in and of Skipper's other helper commands never do, so a role cannot start a process outside its job this way. The program gets the system folder, or the Windows folder for Explorer, as its working folder, never your project's folder, so an open browser does not hold your project's folder. For a link, an opening program that ends with an error code is now refused with the message that tells you to copy the address by hand (before, any ending counted as opened); every check of which address may be opened is unchanged, and the code that you paste after the sign-in is unchanged. Limits: where Windows refuses the leaving (when Skipper itself was started inside another job that forbids it, for example by a launcher with a cap), the start is repeated without it; the browser then opens, but stays in Skipper's jobs and ends when Skipper closes. A Skipper that runs as administrator starts the browser as administrator, as before. Nothing here was run: it is written and read, and the new tests of `skipper-core` and `skipper-confine` have not been compiled or run. Two of them skip themselves under a job that forbids the leaving, which the capped build is, so that a tab shows and outlives Skipper's end has to be seen on a real PC, and has not been.
- **"Lock now" really locks the vault, or says that it could not.** Before, the click on "Lock now" on the Sign-ins page had two steps: Skipper locked its own record first, so that the card said "Locked" at once, and then it locked the sign-in helper, the program that holds the unlocked vault. While the part of Skipper that runs the team was busy at that moment (with the check of what the team needs that runs after a save of the settings, with a team start or with a sign-in start), the second step was skipped without a word, and the click was still answered as done: the card said "Locked" while the helper kept the vault open, and a locked card has no "Lock now" button to click again. A later pass locked the helper by itself, usually soon after the busy part had finished, but until then the vault was open. Now, when that part is busy, a thread of its own waits for it, up to 30 seconds, and locks the helper as soon as it is free; the window never waits. If the busy part does not let go within 30 seconds, the click ends with the message "Skipper is busy with other work and did not take this request in time." and "Try again in a moment.", and the lock stays queued for the next hand-over, so it is not dropped. "Unlock" and the other commands of the vault already waited for that part and are unchanged. Limits: while Skipper waits, the card already says "Locked" although the helper is still open, for as long as the busy part takes, which is usually seconds. A click on "Unlock" in those seconds can be followed by the waiting lock, which leaves the helper locked: the safe side. Nothing here was run: it is written and read, and the new tests of `skipper-app` have not been compiled or run.
- **"Remove from the list" is no longer refused for a briefing session that does not run.** Before, a click on "Remove from the list" could be refused with "A project can be removed from the list only while the briefing session is stopped. It is still running." although no briefing session ran. Cause, as read in the code: the check of what the roles need, which Skipper makes again after every save of the settings and which asks this PC's protection, holds the project's runtime for as long as it runs, and the removal read a held runtime as a running briefing session. The refusal went away by itself when the check ended, so a second click worked. Now the removal asks the way the update button's checks do: the check of what the roles need is told apart from a session that runs, so a running briefing session still refuses the removal, and so does anything else that holds the runtime (a team start, a sign-in start or the start of a helper), but the check alone does not. A start of the team that is on its way now refuses the removal as well, with "Skipper is busy with other work and did not take this request in time." and "Try again in a moment.", because that start could otherwise go on in a project that has left the list; before, this held only by the accident of the held runtime, and not at all between two steps of a start. Limits: this entry describes the code and its tests; it has not been seen on a PC.

Before, the button of the sign-in panel after a failed sign-in said "Erneut anmelden" in German where the account's card says "Neu anmelden"; now both say "Neu anmelden" (the English button, "Sign in again", already matched the card). The name in brackets stays on purpose, because the refusals of a protection tier tell you to look for the rows called `tier_probe`. The sentence of a row is still in its details, which open while the pointer rests on the row.
- **Skipper makes each project's folder itself, so nobody makes a folder and pastes its path.** Before, the first start (step 5, "Project") and "New project …" both asked for the whole path of a folder that existed already. Now every project that Skipper makes the folder for gets its own folder in one main folder, `Skipper-Projects` in your user folder (`%USERPROFILE%\Skipper-Projects`). Skipper makes the main folder when it is missing. It also holds the projects that an import makes, as before.
  - First start, step 5: you give the project a name. The field starts with the word "Project" in it (the German interface has its own word). That is real text, not a grey hint, so you replace it with the name; a field that you empty reads as "Project". Under it the step says "Skipper makes this folder:" with the folder and "(if that name is taken, it gets a number, for example -2)", and "All your projects go into one main folder, ... Skipper makes it when it is missing." There is no path to paste. Skipper makes the folder when you finish the first start. If it cannot, the window goes back to step 5 and says "Skipper could not make the folder for the project." and "Choose a folder that exists already instead, not on the Desktop and not in Documents, then try again." "Use another folder …" brings back the field of before, with its words about "Copy as path" and Ctrl+V and every refusal described above, and "Let Skipper make the folder" leads back. Where Windows does not tell Skipper your user folder, step 5 asks for a folder as it did before.
  - New project: the field "Another folder (optional)" can stay empty. Skipper then makes the folder, named after the project, and says so under the field while you type: "Skipper makes:" with the folder and "(if that name is taken, it gets a number, for example -2)" (before a name is typed: "Skipper makes the folder in ..., named after the project."). A whole path that you type works as before, and every check of "New project" stays.
  - The folder's name is the project's name, with every character other than letters of any alphabet, digits, blanks, `-`, `_` and `.` replaced by a dash and cut to 60 characters. A name with nothing left becomes "Project", and a name that Windows reads as a device (`CON`, `NUL`, `COM1` and so on) gets "Project-" in front. If a folder or a file of that name is already there, Skipper makes `Name-2`, then `Name-3`, and never writes into one that is there. The first project is named after its folder, so a name that was changed shows in the project list as the folder's name.
  - Limits that stay. There is still no folder picker dialog, so "Use another folder …" asks for a pasted path. The lines "Skipper makes this folder:" and "Skipper makes:" show the name before Skipper has looked whether it is taken, so a taken name gives `Name-2` although the line shows `Name`; both lines say so with "(if that name is taken, it gets a number, for example -2)". If a later step refuses the project (for example because its folder lies inside a folder that a role may write to), the empty folder that Skipper made stays, nothing is deleted, and the next try makes `Name-2`.
- **The account card says "Signed in" only with proof.** Before, when Claude Code gave no readable answer to the check that Skipper makes after a sign-in, the card still said "Signed in". Now it says "Sign-in not confirmed", and it says so when the check did not run because a role of the account was working (a check could end that role's session). The card adds "Skipper has not confirmed this sign-in. Check again, or sign in again." and a button "Check again". The button asks Claude Code again, in the account's protective box and with no panel. It does not ask while a role of the account works: "A role of this account is working, so Skipper does not ask Claude Code now: the check could end its session." The first test build recorded "Signed in" without that proof. An account that it marked so keeps the mark until a check runs (a role start makes one) or you sign in again, because "Check again" is offered only on "Sign-in not confirmed".
- **Sign out asks first.** Before, "Sign out" opened the sign-out at once. Now it asks "Sign out account <name>?" and says "Claude Code signs this account out on this PC; roles of this account cannot start until you sign in again." Only the answer "Sign out" opens the sign-out panel and runs it, and "Cancel" starts nothing. This holds on the account's card and on the page Settings, Sign-ins. Sign out still waits while a role of the account runs.
- **The sign-in page opens in your browser by itself.** Before, you copied the address that Claude Code prints in the sign-in panel into a browser. Now Skipper finds that address on the panel's screen and opens it once, in your default browser, from Skipper's own program and never from inside the protective box. It opens only an `https` address on claude.ai, claude.com, console.anthropic.com or anthropic.com (or a subdomain of them) whose path names an authorization, a login or a device step, and only when it has the whole address: an address that is cut at the end of a line, or that is still being printed, is never opened. The panel now says "Claude Code's own sign-in runs here, for this account only. Choose how to sign in; your browser then opens the sign-in page by itself. Finish the sign-in there, and if the browser shows a code, paste it here with Ctrl+V." While Skipper has the address, the panel offers "Open the sign-in page again". The tests use output made up to look like Claude Code's. Nobody has captured the real output on a real PC yet, and when a program breaks the address short of the screen's right edge, Skipper opens nothing. Then copy the address from the panel by hand, as before.
- **A Skipper service whose start the protection tier refuses stops at once and says why.** Skipper's own helper sessions are called services. Today there is one, the Briefing's summary session, which works only while "Live summary" is on and a team run is open (after you press Start team). A start that the choice of a protection tier refuses, for example "No protection tier works on this PC, so this service does not start." or "This service cannot start in the weak protection tier while Skipper holds saved sign-ins.", is not something that trying again can change. Before, such a start counted as a failed run, Skipper tried again at the next trigger, and the service stopped only after three failed runs in a row, with a card that gave no reason. Now the service stops at the first refusal. Its card in Needs you, "A Skipper service stopped", has two lines under it: "Reason: ..." with the sentence of the refusal and "What to do: ..." with the way out. Each way points to the Log page and its newest "tier_probe" rows. The sentences are the words of a service: they do not say "role" and do not tell you to choose another protection tier, which a service does not let you do. When the saved sign-ins are the cause, the way names the step that keeps your data first: "Get the strong protection tier working on this PC (the Log page and its newest “tier_probe” rows say why it does not), or delete the saved sign-ins. Then press “Try again”. Skipper deleted nothing." Skipper keeps the reason only while it runs: after a restart the card still stands, but without those two lines. A limit that stays: the switch "Live summary" is greyed out until its check, PRB-87, has passed, and that check has not run yet, so a test build starts no service. This entry and the three after it describe the code and its automated tests, not something that a test build shows today.
- **The card of a stopped service no longer says that the service failed three times in a row.** A service can now stop for two causes, three failed runs in a row or one refused start, so the card says only what holds for both: "One of Skipper's own helper sessions could not do its work, so Skipper does not start it again by itself. When Skipper knows why, the details of this card say so. It starts again when you press Try again on its row on the Terminals page." In the German interface the card also names the button as the row does ("Noch einmal versuchen").
- **The row of a stopped service on the Terminals page shows why it stopped.** After the state word, the account and the last run, the row has one short line with the same reason as the card. Where the row has no room the line is cut, and resting the pointer on it shows the whole sentence. A stop for which Skipper has no reason shows no line: a stop after three failed runs, and a stop from before Skipper was restarted. "Try again" is on the row as before. It lets the service work again and starts nothing by itself: the service starts at its next trigger, and stops again at once if the tier choice still refuses it.
- **A stopped service reads "Stopped".** The state word of the Briefing service was "Stopped after three tries" (German: "Nach drei Versuchen gestoppt"), also for a service that one refused start had stopped. It now reads "Stopped" ("Gestoppt"), and where Skipper knows why, the line beside the word on the Terminals row says it. The word stands on the Terminals row, on the line "State" of the service's own page, and in what a screen reader reads for the service's row in the sidebar.
- **Skipper has a new icon, the Route-S logo.** The logo is one S-shaped route line with a large blue dot at the bottom left (the start) and a small light dot at the top right (the goal), on a dark rounded square. It is the icon of `skipper.exe`, which Explorer, shortcuts and the file's properties show, and the icon that every window of Skipper is given. The icon of `skipper.exe` holds eight sizes: 16, 20, 24 and 32 pixels as drawn by hand (a thicker line and shapes that sit on the pixel grid, so that it stays sharp and the blue dot stays round), 40, 48 and 64 pixels averaged down from the 256 pixel logo, and the 256 pixel logo itself. The README shows the logo at its top, and [the logo page](brand.md) says what it means, which colours it uses, how much room it needs, how small it may be and which file is for what (the picture files are in `docs/brand/`).
- **The sidebar mark is the logo in its own colours, and the title bar shows its small icon.** At the top of the sidebar, beside the name "Skipper", the mark is the logo as a picture. It looks the same in the light and the dark theme. It is 16 points wide at Windows' normal text size (a larger "Text size" in Windows makes it larger, and the picture follows), and it shows the hand-drawn picture that matches its size on your screen: 16 pixels at a Windows scaling of 100 %, 20 at 125 %, 24 at 150 % and 32 at 200 %. Between those it shows the next larger hand-drawn picture, scaled down (at 175 % the mark is 28 pixels wide and shows the 32 pixel picture). Where the mark would be wider than 32 pixels (above 200 %, for example 225 % or 250 %) the 256 pixel logo is scaled down. The title bar of the main window shows the hand-drawn picture of its own small-icon size in the same way (16, 20, 24 or 32 pixels at 100, 125, 150 or 200 %, and at 175 % the 32 pixel picture, which Windows scales to the 28 pixels it wants). Skipper sets it once the window has had the focus, and sets it again when you move the window to a screen that needs another size. Until then the title bar shows the icon that the window library makes from the 256 pixel logo, and it keeps that icon above 200 % (for example 225 % or 250 %). Limits: the taskbar button of the running program also shows the icon that the window library makes from the 256 pixel logo, not a hand-drawn size; the windows that you detach from the terminal panels, the window that reports a fatal error and the preview program keep the 256 pixel logo, which Windows scales for their title bars. The tests check which picture is chosen and when it is sent. That Windows then shows the pictures as described here rests on a reading of the code of the window libraries, not on a look at a real screen.

## 0.1.0-test.1

Not published.

### In code

- Roles as real Claude Code terminals in panels, the role cards, the Needs you inbox and the saved layout.
- The first-run steps, the starter team of eight roles and the empty start.
- The board, the task board and the knowledge base, stored as plain files, and the Briefing.
- The final approval by a person's click, and the check before a push.
- Pacing of new starts, on by default in the mode "suggest". The weekly table atop the Accounts page, and the weekly warnings at 85 % and 93 % of an account's week, each once for each weekly window. One card for each account stands for the highest level reached: the card of the weekly gate (93 %, or a projection to 93 %) takes the place of the card of the first warning. A weekly value reads "unknown" once its week has ended.
- Accounts shared with you: Skipper never pushes an account that it sees you use outside Skipper (it stays shared to the end of that weekly window, in every project and after a restart), or that you mark with the line `shared = true` in `pacing.toml`. There is no button for the mark yet.
- The hardware scan, the caps and the reserve.
- Model settings with the automatic choice of model and effort, on by default. Each role card holds the limits of the choice (start row, lowest and highest model and effort, when ultracode and ultrathink may start), saved from the window. A start that waited in the queue takes the choice as it stands when it starts. A settings page for Claude Code's own settings, checked against the documentation of Claude Code 2.1.318.
- Auto mode of Claude Code is switched off in every role (`permissions.disableAutoMode`). A role starts in `acceptEdits` unless you picked another of the four modes that Skipper offers for it. The version floor, Claude Code 2.1.295, does not rest on auto mode.
- Updates compare versions as semantic versioning does (`0.1.0-test.9` is older than `0.1.0-test.10`), so "Roll back" and the pruning of old backups pick the right version.
- The protective box (a job object and an AppContainer) and its weaker fallback. Their probes have not run, so every role card says "not verified".
- Connections through Skipper, the vault and the sign-in helper, for servers on the internet. The Windows Hello layer is built but switched off until its probe (PRB-96) has run: the settings refuse the choice, and the vault unlocks with your Windows sign-in. The idle lock counts from the unlock or the last use. A local program through Skipper is refused for now.
- Import from files: a folder or ZIP of Markdown or Obsidian files, a Notion export ZIP and a Trello export. A preview comes first and always offers Cancel, and an import can be undone. An import can go into a new project, which Skipper makes first in `Skipper-Projects` in your user folder.
- Import from Linear, GitHub Issues and the Notion API. The import window saves one sign-in for the import, bound to the service's own address, and Skipper's sign-in helper reads the service. This has not been tried against the real services, so the tiles of Linear and GitHub Issues and the button for the Notion API carry the badge "new".
- The maintainer role for pull requests and issues from outside.
- Several projects open at once.
- Updates. Skipper looks for updates by itself while the setting is on, which is the default; the release source is empty until the first release, so nothing is fetched.
- The per-user installer: the setup file, the install and uninstall without administrator rights, and the repair of a folder that an update left half finished.
- English and German, light and dark.
- The text of the window follows Windows' "Text size" (Settings, Accessibility, Text size), also while Skipper runs. It grows with the setting up to 200 percent, the most the design allows, so a larger setting stops there.
- The English user documents: install guide, user guide, privacy page, this changelog, release guide, probe guide and the list of tested Claude Code versions.

### Not built yet

- Import from Jira Cloud through its service. The sign-in prompt has no place for the e-mail that Jira needs beside the token, so the import window hides Jira's sign-in step and an import from Jira cannot be started.
- Flows (editable templates and the "Build cycle" starter flow), the timeline and the stall view.
- Protection through Docker, WSL or an address filter.
- Export as Markdown or CSV, and ready-made connection templates.
- Skipper's own skills: 17 are written and none is shipped.
- Code signing and a release. Nothing is published.

### Known limits

- No probe counts as passed. `cargo xtask stage1-check` keeps every item open (it runs once the code and the probe sheets are published). [Tested Claude Code versions](tested-versions.md) says what is known about Claude Code.
- The protective box is weaker than a Linux container, and the internet stays open in it. [SECURITY.md](../SECURITY.md) lists the limits.
- Builds are unsigned, so Windows may warn before it runs one.
